# 框架·5 四问定动作

## 这步为什么存在
**自动化是最后一步，不是第一步。** 顺序反了 = 在优化一个本不该存在的东西——做了一堆工具去伺候一个错误流程，越自动越深地跑偏。这一步就是那把尺子。

## 顺序（四问，依次问，不许跳）
1. **该不该有**（不是「怎么优化」）
   - 这个动作本身该存在吗？删掉它，问题还在吗？
   - 答"该删"→ 就删，**到此结束**，不进入第 2 问。
2. **能不能少一步**
   - 能不能把中间某一步去掉、合并、挪到别处？
   - 答"能"→ 先做完再做自动化。
3. **能不能换人 / 换机器**
   - 能不能交给别人做？能不能交给机器做？
   - 答"能"→ 先换，再谈自动化。
4. **能不能更快**
   - 只能更快了吗？加速现有流程（并行、缓存、缩短等待）。
5. **才轮到自动化**
   - 前四问答完都"不能省了"，才做自动化步骤（`type: automation`）。
   - **自动化前置条件**：①高频 ②已验证有效 ③有明确入口/退出码/输出。三条缺一不做。

## 判断点
- 跳过第 1 问直接谈自动化 → **停**，先问该不该有。
- "自动化"其实是在替一件**不该做**的事提速 → 回第 1 问。
- 一个操作只出现过一两次 → 不做自动化条目，先当一次性方法跑（`方法/`），重复了再升级。
- 想自动化的东西有判断点（靠语义）→ 拆：**判断留 method，能跑的留 automation**。别硬把判断塞进脚本。
- 已经做成 skill 了 → 查「与 skill 的分工」：每轮都要看见 → skill；遇某类问题才查 → 方法库。同内容只许一个落点。

## 失效信号
- 库里出现一堆"自动化"条目，但每个一个月用一次 → 自动化跑在了前面。
- 自动化条目里塞着长篇判断和散文 → 类型判据错了，那条该是 method。
- 四问里第 1 问的答案永远是"该有" → 从没真问过。

## 上游输入 / 下游输出
- 上游：一个想固化/自动化的操作。
- 下游：要么"删了/合并了/换人做了"，要么一条合格的 `自动化/*.md` 条目。
