# 框架-长程任务打卡协议

## 这条为什么存在

出处是 dsh-routing-suite（2026-10-28 评估后决定不装，思路吸收）。它的公开研究位给过实测数据：**长程任务无协议链时，晚段出现"1 工具 / 0 读图"式的懈怠**——模型勤勉度随轮次衰减，带协议链的会话全程在线。

我们自己也有同款现象的变体：调试止损线（同 bug 调 3 轮没解决就停）、"收工判据按秒不按轮"（慢速生成每轮涨几个字被误判稳定、交出半句）——本质都是**执行段缺乏外部结构，靠感觉收工必翻车**。

## 协议五段

1. **脑暴对齐**：开工前不出计划先出选择题——方向分歧列成 2–3 个选项让决策者勾，不自由发挥、也不逐条问细节。
2. **北极星定稿**：一句话写死"成功长什么样 / 验收标准是什么"，写进任务文件首行。验收标准先于动手存在。
3. **规格化计划**：拆成带编号的条目清单，每条可独立验收，落到文件（进度/任务文件），不写脑子里。
4. **打卡执行**：每完成一条，在清单上标完成 + 留证据（文件路径 / 实测输出行 / 测试结果）。打卡防的是"感觉做完了"。
5. **收官 + 红队门**：全部打卡后，换"挑错者视角"过一遍终验清单（见下），过了才写进度、交收。**不许跳过终验直接宣布完成。**

## 任务分型（开工第一步）

- **修护/维护类**（改 bug、迁移、修正）→ 先出规格再动手，规格错了全白改。
- **新建/构建类**（写探针、做页面、做课件）→ 可先做骨架再补规格，但打卡制和红队门**不豁免**。

## 红队门检查清单（收官必过）

- [ ] 每条计划都有完成证据——是"实测过"，不是"应该没问题"
- [ ] 验收结果逐条对过北极星，没有偷偷降低标准
- [ ] 自证跑过（测试 / 实测数字），且改过一处就重跑一次
- [ ] 交付物落点正确（给用户的放桌面/对话，AI 自己的归档）

## 不适用

1–3 步小任务、纯问答——套协议是花架子，直接做。
