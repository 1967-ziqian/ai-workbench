# 框架·1 发现

## 这步为什么存在
AI 判断「该不该用某条方法」靠的是文件里的 frontmatter，不是记忆、不是中心注册表。没有这一步，库就只是文件夹。

## 顺序
1. **知道有这库**：`上下文/S3-索引/_默认.md` 里有「方法库」条目 → 知道 `` 存在。
2. **进 `_INDEX.md`**：拿全部条目的一行摘要（名字｜triggers 一句｜when-not 一句｜路径｜依赖）。**只读索引，不遍历目录。**
3. **按 triggers 初筛**：用户的话/当前情境与哪几条的 triggers 对得上 → 那几条是候选。
4. **点开候选的 `.md`**：读 frontmatter 全文 + 正文。

> 血缘：Matt Pocock 的技能体系——靠 frontmatter 被发现，不靠中心注册表。方法库借的是这个骨架。

## 判断点
- 索引里没有一行提到相关能力 → **不要自己去翻目录**，去 `_INDEX.md` 补一行（登记见下）。
- 同一问题命中 ≥3 条 → 按 `triggers` 的**具体性**排，先用最具体的那条，别一次套好几条。
- 候选条目读不出 frontmatter → 该条目坏了：当场记进复盘错题册，并按「框架·4 留痕与回流」修它。

## 失效信号
- 读了 `_INDEX.md` 才知道库里有什么 → 说明索引没写全（**索引是索引，不是目录**）。
- 每次都要遍历目录才找到东西 → 同上，成本会高到 AI 永远不再发现。
- 命中了却没点开 → triggers 写得太抽象，没法在真实语境里对上。

## 上游输入 / 下游输出
- 上游：S3 索引里的库条目。
- 下游：候选条目清单 → 交给「框架·2 判命中」。

## 登记一条新条目（写侧）
1. 写 frontmatter：`name`（唯一键）/ `title` / `type` / `description` / `triggers` / `when-not` / `source` / `最后核对`（YYYY-MM-DD）。
2. 放进对应目录：`方法/`（method）、`自动化/`（automation）、`素材/`（material）。**一个文件不许兼两型。**
3. 在 `_INDEX.md` 补一行：**triggers 一句 + when-not 一句 + 路径 + 依赖**——只写名字等于没登记。
4. 新术语先查 `GLOSSARY.md`，没有再补一条。
