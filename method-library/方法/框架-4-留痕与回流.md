# 框架·4 留痕与回流

## 这步为什么存在
**读 ≠ 学会。** 读完套用完就散场，库永远停在原地——每次都从零开始，而坑重复踩。所以必须有「用了什么、效果如何、坑在哪」的留痕与回流。

## 顺序
1. **任务首行留痕**：
   ```
   判据｜命中索引：方法库/无
   ```
   命中了具体条目就写条目名（如 `方法库/方法/框架-2-判命中`），没命中写「无」。**不命中也要写**——"没有"和"没查"是两回事，不写就分不清。
2. **用完记一句**：这条方法这次用下来顺不顺、在哪卡住。
3. **坑 → 复盘错题册**：踩了坑、发现某条方法的判据不对、某个步骤有歧义 → 记进 `../self-review/错题册.md`（带 id 和状态机：已验证 / 待验证 / 已挂载）。**失败的教训不进本库**。
4. **可泛化的成功 → 新方法**：同一条方法被反复用、反复有效 → 抽成新 `.md` 进 `方法/`；高频且已验证的操作 → 抽成新 `.md` 进 `自动化/`（见「框架·5 四问定动作」的自动化前置条件）。
5. **改条目**：发现某条方法的 `triggers`/`when-not`/正文不准确 → 直接改那一篇，并更新 `最后核对` 日期。**库要自己长大，靠的是改条目，不是攒条目。**

## 判断点
- 坑的根因是"方法不对"还是"没用对"？前者改方法，后者改用法——改错地方等于白改。
- 这个经验够不够格进库？**只出现一次**的偶发情况不急着写成方法（会污染库）；重复出现且可泛化才写。
- 该沉淀成 method 还是 automation？判据在「框架·5 四问定动作」：有独立入口/退出码 → automation，只有顺序与判断点 → method。

## 失效信号
- 任务做完，库里什么都没多、什么都没改 → 库在空转。
- 留痕只写"命中"、不写命中了哪条 → 无法统计命中率，等于没留。
- 坑全记在脑子里、没进错题册 → 下次自然召回不到。

## 上游输入 / 下游输出
- 上游：执行结果与踩到的坑（来自「框架·3 套用」）。
- 下游：更新后的条目 / 错题册条目 / 新的命中统计 → 库长大。
