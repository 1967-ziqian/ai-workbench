# 框架·2 判命中

## 这步为什么存在
方法库最大的失败模式不是「方法不够好」，是**硬塞**——把一条不合适的排查完以后硬套上去，任务被拖慢，结论还跑偏。所以「用不用」必须是一个**显式判断**，不能省。

## 顺序
1. **对 triggers**：用户的话、当前情境，逐条对 `triggers`。
   - 命中 ≥1 条 → 进入第 2 步。
   - 一条都对不上 → **默认不套用**，走通用能力。
2. **对 when-not**：逐条对 `when-not`。
   - 命中任一条 → **直接跳过**，哪怕 triggers 也命中。**when-not 优先级更高**——它是「这条明确不适用」的显式声明。
3. **两者都不明确** → 默认不套用。**不确定时不用**，比误用便宜。
4. 记下判断结果：命中了哪条、命中的是哪一条 triggers；没命中就记「无」（交给「框架·4 留痕与回流」）。

## 判断点
- triggers 命中但 when-not 也命中 → **跳过**。冲突时以 when-not 为准。
- 命中多条 → 用**最具体**的那条（triggers 描述的场景更窄的那条），别叠着用。
- 命中的是「像」而不是「是」→ 按不命中处理。方法库宁可少用，不要养成硬塞的习惯。
- 候选是自动化步骤（`type: automation`）→ 它有明确入口，先跑它，看输出再决定要不要套方法。

## 失效信号
- 每次都靠"感觉"决定用不用，事后说不清为什么 → 没做语义匹配，退化成随机抽签。
- 频繁出现「这方法不适用」→ `when-not` 没写全，补上；别怪方法本身。
- 命中了但执行后发现方向完全不对 → `triggers` 写得太宽，收窄它。

## 上游输入 / 下游输出
- 上游：候选条目清单（来自「框架·1 发现」）。
- 下游：一条确认可用的条目（或「不套用」的结论）→ 交给「框架·3 套用」。
